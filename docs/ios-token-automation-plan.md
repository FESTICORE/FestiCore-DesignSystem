# iOS 디자인 토큰 자동화 설계 (#1)

## 목표

`tokens/`의 DTCG 원본을 검증하고 light/dark iOS Swift 토큰을 결정적으로 생성한다. PR에서 생성물 차이를 검사하고, `main` 변경 뒤 FestiCore-iOS의 디자인 모듈에 변경 PR이 자동으로 열린다.

## 원칙과 경계

- `FestiCore-DesignSystem`의 JSON을 원본으로 유지한다. Joongna/design-system과 SWYP-design-tokens의 Style Dictionary v4 검증·생성·CI 구조를 참고하되, 다른 앱의 Figma 파일 ID·이미지·비밀값은 복사하지 않는다. 사용자가 지정한 Attendance의 PretendardVariable.ttf와 폰트 등록 방식은 iOS 디자인 모듈에 적용한다.
- `$themes.json`의 light/dark 토큰 세트 목록으로 두 개의 독립된 토큰 트리를 만든다. `enabled` 세트만 출력하고 `source` 세트는 별칭 해석에만 사용하며 `disabled` 세트는 무시한다. 같은 트리 안의 중복 경로, 미해결·순환 별칭, 잘못된 타입·색·치수·타이포 값은 빌드 실패로 처리한다. 두 테마의 semantic color 경로 집합은 정확히 같아야 하며, 누락 경로가 있으면 실패한다.
- iOS 18을 대상으로 모듈 이름은 DDDDesignKit 구조에 맞춰 `FestiCoreDesignKit`으로 둔다. 색상은 Swift 코드의 `public extension Color`, `public extension UIColor`, `public extension ShapeStyle where Self == Color`에 동일한 semantic 이름으로 생성한다. 각 `UIColor` 속성은 trait collection에 따라 light/dark 값을 선택하고 SwiftUI `Color` 속성은 해당 동적 색상을 감싼다. 기존 `FestiCoreColor` API는 제거하고 호출부·테스트를 함께 이전한다. `.xcassets`를 생성하지 않는다. spacing/radius는 기존 API를 유지하고 typography는 `FestiCoreTextStyle` enum case로 생성한다. 화면에서는 SwiftUI modifier 체이닝과 `Color.name` 또는 `.foregroundStyle(.name)`을 사용한다. 생성기는 수작업 SwiftUI 확장 파일을 덮어쓰지 않는다. 생성 파일 상단에는 파일명·모듈명·고정 작성자 `FestiCore-DesignSystem generator` 헤더를 넣고 필요한 주석만 한국어로 쓴다. iOS 디자인 모듈 테스트는 공개 색상 스냅샷의 모든 이름을 `Color.name`/`UIColor.name`/`ShapeStyle` 경유로 실제 참조해 SDK·수작업 확장과의 모호성을 컴파일로 확인한다.
- 원본의 typography family 별칭 정보는 보존한다. base·point 모두 Pretendard를 사용하지만 각각 `{font-family.base}`·`{font-family.point}` 별칭을 요구한다. iOS 디자인 모듈은 Attendance와 같은 PretendardVariable.ttf를 `Resources/FontAsset/`에 포함하고 AppDelegate에서 한 번 등록한다. SwiftUI 폰트 modifier는 토큰의 크기·굵기·자간과 등록된 Pretendard를 사용하며 배수형 line height로 계산한 행간을 modifier 체이닝으로 적용한다. `px`는 iOS `pt`, 자간의 `em`은 글자 크기와 곱한 `pt`로 변환한다. `%` 등 지원하지 않는 단위는 실패한다. safe-area는 런타임 값 대신 사용하지 않는다.
- 이번 iOS 출력은 semantic color, spacing, radius, typography로 한정한다. `source` 원자 색은 semantic 별칭 해석에만 쓰며 출력하지 않는다. gradient, breakpoint, opacity/state, safe-area는 원본에 보존하고 iOS 생성 대상에서 제외한다. 따라서 theme별 dimmed opacity 차이는 별도 후속 설계로 다룬다.
- spacing, radius, typography는 테마에 관계없는 공통 값이다. 두 트리에서 별칭을 해석한 뒤 경로와 값이 완전히 같은지 검사하고 한 번만 출력한다. 테마별 값 차이, 변환된 Swift 이름 충돌, 공개 semantic 색상 이름 목록의 스냅샷 이탈은 테스트 실패로 처리한다.
- 생성 산출물은 `generated/ios/Sources/`에 저장한다. `npm run build`는 각 테마의 DTCG 입력을 검증·해석한 후에만 `generated/ios/`를 교체한다. 전용 Swift 작성기가 결과를 직렬화한다. 숫자 자릿수·키 순서를 고정하고 타임스탬프는 넣지 않는다. `npm run check`는 재생성 후 `git status --porcelain -- generated/ios`가 비어 있어야 성공하며 추가·누락 파일도 실패한다. 잘못된 fixture, theme 경로 불일치, source 미출력, `em`/배수 단위, 제외 범위, 생성 파일 헤더와 xcassets 부재를 테스트한다. Node 버전은 `.nvmrc`/`engines`와 CI에서 고정한다.
- `FestiCore-DesignSystem` PR CI는 typecheck, 테스트, build/check를 수행한다. `main` 반영 시 iOS 저장소가 공개 원본을 주기적으로 확인한다. `main` SHA를 한 번 확정하고 그 SHA의 원본 JSON과 `generated/ios/`만 내려받는다. iOS 디자인 모듈에는 `Generated/` 폴더를 두지 않는다. `Colors.swift`, `UIColors.swift`, `ShapeStyle+.swift`는 `Sources/Token/Color/`로, `FestiCoreLayout.swift`는 `Sources/Token/Layout/`로, `FestiCoreTypography.swift`는 `Sources/Token/Typography/`로 각각 복사한다. 원본 JSON은 `Tests/Resources/Tokens/`에 복사한다. `Resources/ImageAssets.xcassets`는 앱 이미지용 빈 카탈로그로 유지하며 토큰 동기화 대상에서 제외한다. iOS에서 npm으로 다시 생성하지 않는다. `TokenSnapshot/.source-sha`에 원본 SHA를 기록한다. 생성물 파일 목록이 바뀌면 양쪽 저장소의 허용 목록과 이전 파일 삭제 규칙을 같은 변경에서 수정하고, 불일치는 자동 동기화를 실패시킨다. 압축 경로·확장자를 검증하지만 내려받은 Swift는 이후 iOS 빌드·테스트에서 컴파일·실행되므로 신뢰 경계로 취급한다.
- 동기화 워크플로는 고정 브랜치 `chore/design-tokens-sync`를 갱신하고 기존 PR을 재사용한다. 열린 PR 또는 `develop`의 `.source-sha`와 동일한 SHA는 건너뛰고, 변경된 SHA의 선후 관계는 GitHub commit ancestry로 확인해 구버전 갱신을 막는다. `concurrency: { group: design-token-sync, cancel-in-progress: false }`로 직렬화한다. iOS `GITHUB_TOKEN`으로 만든 PR은 PR 이벤트 CI를 자동으로 시작하지 않으므로, 동기화 워크플로에서 `./make generate`와 디자인/Stage 테스트 및 커버리지 검증을 먼저 수행하고 그 결과를 PR 본문·아티팩트에 기록한다. 검증 실패 시 PR을 열지 않는다. 읽기 작업의 기본 권한은 `{}`이고 PR 작성 job에만 `contents`/`pull-requests: write`를 준다. 필요한 상태 기록 job에는 `checks: write`, 실패 댓글 job에는 `pull-requests: write`를 명시한다. Actions는 커밋 SHA로 고정한다. 수동 `workflow_dispatch`도 제공한다.
- 테스트 job은 검증된 다섯 Swift 파일·원본 JSON·SHA만 아티팩트로 올리고 digest를 기록한다. PR 작성 job은 digest와 `TokenSnapshot/.source-sha`를 다시 확인한 뒤 허용된 토큰 경로만 커밋한다. 기존 대상 파일은 정확한 생성기 헤더가 있을 때만 덮어쓰고, 다른 위치의 수작업 Swift 파일이 생성 파일명을 사용하면 실패한다. 다른 `Sources/` 컴포넌트와 `Resources/`는 보존한다. 이 digest는 job 사이의 전달 오류 감지 용도이며 공급망 신뢰 증명으로 해석하지 않는다. 검사 결과는 PR head SHA에 동일한 필수 check 이름으로 기록하고 재푸시할 때 다시 실행한다. 실패하면 기존 동기화 PR에 실패 SHA와 Actions 링크를 댓글로 남긴다. 압축 파일은 예상 경로 아래의 일반 파일만 허용하고 심볼릭 링크, 하드 링크, 절대 경로 및 `..` 경로를 거부한다.

## 순서와 검증

1. `feature/design-token-automation` 브랜치에서 검증기·생성기·fixture 테스트와 npm lockfile을 추가한다. `npm ci && npm run typecheck && npm test && npm run check`를 통과시킨다.
2. DesignSystem PR CI를 추가하고 `main`에 PR을 제출한다. CI 성공 후 병합한다.
3. FestiCore-iOS에 지정 SHA의 원본·생성물 fetch, 검증, 파일별 토큰 교체 및 PR 워크플로를 추가한다. 동기화 workflow 안에서 `./make generate`, 디자인 모듈 테스트, 전체 Stage 테스트와 커버리지를 확인하고 최초 동기화 PR을 실제로 열어 결과를 검증한 뒤 이슈 #1을 닫는다.
4. 후속 `fix/swift-color-tokens` 브랜치에서 `FestiCoreColor`와 xcassets 생성을 제거하고 `Color`/`UIColor`/`ShapeStyle` 소스, 고정 헤더 및 회귀 테스트를 만든다. DesignSystem PR을 먼저 **merge commit**으로 `main`에 병합해 기존 SHA의 ancestry를 유지한다. 그 사이 iOS `feature/core-ui-modules` 브랜치에서 `FestiCoreDesignSystem`을 `FestiCoreDesignKit`으로 변경하고 기존 색상 호출부·테스트·동기화 목록을 이전하되, DesignSystem의 새 `main` SHA가 확정되기 전에는 iOS PR을 병합하지 않는다. 수작업 버튼·구분선·타이포 확장도 `Sources/Component`와 `Sources/Token`의 파일별 구조로 분리하고 SwiftUI modifier 체이닝을 유지한다. 이전 iOS `Generated/` 전체(옛 `.source-sha`, `FestiCoreColor.swift`, 색상 xcassets 포함)를 삭제한다. 병합 직후 확정된 `main` SHA의 생성물·원본만 iOS 동기화 스크립트로 가져와 `TokenSnapshot/.source-sha`를 기록한다. 이어 `npm ci && npm run typecheck && npm test && npm run check`, `./make generate --no-open`, `xcodebuild build -scheme FestiCoreDesignKit -configuration Stage -destination 'generic/platform=iOS Simulator'`로 검증하고 iOS PR을 연다. 중간에 예약 동기화가 실행되어 기존 호출부와 불일치하면 PR을 만들지 않고 실패로 남긴 뒤 iOS 병합 후 수동 재실행한다. 이전 SHA의 열린 동기화 PR은 iOS 병합 전에 닫는다. SHA가 `diverged`이면 자동 갱신을 중단하고 원본 커밋 관계와 기준 SHA를 수동 확인한다.

## 제약과 리스크

- GitHub schedule은 정시 실행을 보장하지 않는다. 수동 `workflow_dispatch`는 즉시 검증 경로다. Figma publish 실시간 웹훅은 Figma 인증·중계 서비스가 제공되지 않았으므로 이번 자동화에서 제외한다.
- 공개 원본이라 fetch에 PAT가 필요 없지만, GitHub 저장소의 Actions 설정이 `GITHUB_TOKEN`의 PR 생성을 허용해야 한다. 제한되어 있으면 워크플로 실패로 남기고 설정 또는 별도 권한이 필요하다.
- iOS 생성 코드가 기존 스냅샷과 의미상 다르게 나오면 차이를 먼저 검토하고, 원본 토큰이나 변환 규칙 중 어느 쪽을 고칠지 결정한다.
